# decode_action 故障修复与扩展分析

日期：2026-11-21。分析基线：`foglamb/decode_action` 的 `e809ff4080e5ad0b3eacfe4e8ebba9f7154d8935`。本次保留原始输入和历史输出，修复通过独立分支交付，不自动合并到 `main`。

## 结论

问题涉及运行时依赖、解码深度、输入识别、CLI 参数和结果发布，不能仅凭生成了输出文件就判断功能恢复。最明确的内容故障在 Python：原输出的日期注释后仍以 `BZh9` 开头，说明只处理了外层 gzip，内层 BZip2 数据被当作脚本保存。

修复后，仓库自带 Python 样例恢复为 62,942 字节的可解析源码，包含 55 个函数、1 个类。JS 当前样例以及历史失败运行对应的样例，生成结果的规范化 AST 与修复前可用基线一致。本地 28 项测试通过。

## 故障与修复证据

| 问题 | 原实现与影响 | 本次处理 |
| --- | --- | --- |
| Node 与原生扩展不兼容 | `isolated-vm` 4.7.2 在本机 Node 24.15.0 下编译失败；相同依赖在 Node 20.20.2 下可安装 | CI 沿用兼容性固定的 Node 20；新增锁文件，用 `npm ci` 安装。JS 插件按需导入，Packer/common 不再先导入全部原生插件 |
| Python 只解一层压缩 | 原流程一次 Base64 加一次解压；真实样例组合了 gzip、bz2、lzma、zlib 和后续多层脚本包装 | 按白名单 AST 的调用顺序静态解释压缩和编码，保留跨层使用的静态变量与单参数 lambda |
| Python 正则匹配过窄 | 仅处理 `base64.b64decode('...')` 的特定写法，漏掉 bytes 字面量、别名与双引号等情况 | 改为语法树解析，支持静态变量、字节串、别名、反转切片和拼接 |
| 明文被误当成 Base64 | 重复猜测 Base64 会把 `pass`、`test`、`None` 等有效文本继续转成非源码字节 | 只对显式编码调用解码；隐式压缩识别依赖流头，不猜测明文 Base64 |
| JS 参数未生效 | 原 npm 的 `deob`、`deso`、`desov7` 传了 `-t`，主入口却不处理该选项 | 完整解析 `-i/-o/-t/-h` 及长参数；指定插件不匹配、未知选项、缺少值返回非零状态 |
| JS 无转换结果时无新文件 | 旧逻辑不写输出，调用方可能误读旧输出 | 自动模式无转换时明确记录原文回退；失败的显式插件不伪装成成功 |
| 输入内容特定字符串触发全局跳过 | 原入口出现 `smEcV` 就跳过全部插件 | 删除无格式依据的字符串短路；添加回归覆盖 |
| 无变化提交失败 | 无条件 `git commit`，没有文件差异时非零退出 | 检查暂存差异后再提交；输出头部固定，避免仅时间戳导致重复提交 |
| 一种语言失败阻断另一种 | 原单任务顺序执行 Python 与 JS | 拆为两个矩阵任务，`fail-fast: false`；只归档本次生成的独立输出目录 |
| 提交失败看不到解码成果 | 输出依赖写回仓库才能查看 | 先以 artifact 保留本次成果；后续测试或提交失败仍能取回已生成文件 |
| 并发运行写回旧输入结果 | 解码期间分支可能发生变化 | 发布前对比运行 SHA；分支已前移则保留 artifact，跳过旧结果提交；不强制推送 |

历史运行 #23、#22 的步骤记录显示失败在依赖安装/JS 执行阶段，但完整日志已返回 410 Gone。因此不能声称已经拿到那两次运行的原始异常堆栈。Node ABI 问题是本次独立复现、并与后续固定 Node 20 的成功运行相符的结论。

## 新增解码能力

### JavaScript Packer

新增 [静态 Packer 插件](../src/plugin/packer.js)，识别经典参数结构、字典进制和标准替换循环，不执行输入中的打包函数。

- 支持字典进制 2–62 的已识别编码结构、嵌套 Packer，最多 8 次展开。
- 区分标准 Packer 的同时映射分支和简化替换循环，避免字典词本身恰好也是 token 时被再次替换。
- 替换词中的 `$&`、`$1`、`$$` 保持原样。
- 拒绝混有其他独立语句的输入，避免静默丢弃旁边代码。
- 输出限制 16 MiB，并限制简化循环的替换工作量。

### Python 静态数据包装

[Python 解码器](../src/decode.py) 支持：

- 标准和 URL-safe Base64、Base16、Base32、Base85、Ascii85。
- `bytes.fromhex`、`binascii.unhexlify`，以及限定形式的 ROT13/hex/Base64 `codecs.decode`。
- gzip、bz2、zlib、lzma 及其组合；有限个拼接压缩成员。
- `str`/`bytes` 字面量、模块/函数导入别名、静态变量、拼接、反转切片、文本 encode/decode。
- 静态单参数 lambda、compile 数据包装、简单 try/except 包装。
- 单层 zip/切片/join 生成式中的有限整数运算及 chr/ord。仓库样例所用的 UTF-8 双字节字符映射已加入独立回归样本。

只解释显式白名单表达式，不对输入调用 `exec`、`eval`、`compile` 或动态导入。大小、次数、整数与 AST 深度均有上限；普通业务代码和未知包装保留在当前恢复层，不继续尝试执行。

真实样例的恢复链概括为：

```text
Base64 → gzip → bz2 → lzma → zlib
→ UTF-8 字符映射
→ 多层反转 Base16 / zlib，复用静态 lambda
→ 多层 try 包装、Base64 / gzip / bz2 / zlib
→ 可解析的 Python 源码
```

## 范围与后续候选

本次没有声称解决全部混淆格式、破解未知 AES 密钥，或反编译 marshal/pyc。优先候选是 AAEncode/JSFuck、受限 JS 字面量包装，以及按真实样例扩展已有 AST 插件的版本规则。每种新格式应先建立预期输出与反例，不能仅靠“文件已生成”验收。

原有 JS 插件仍有直接动态求值路径。此次发布拆分降低了解码过程直接持有仓库写权限的风险，但没有把全部旧插件改造成安全沙箱，也不应据此把任意输入代码放到带敏感凭据的自托管环境执行。
